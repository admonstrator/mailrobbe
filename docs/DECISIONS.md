# Decisions

Binding decisions for Mailrobbe beyond docs/SPEC.md. New entries get the next number; a changed decision gets a new entry that names the one it replaces.

| No. | Question | Decision | Date |
|---|---|---|---|
| D1 | Frontend stack | React + TypeScript + Vite, built as a static bundle served by FastAPI. | 2026-10-20 |
| D2 | Alias merging (SPEC 9) | Automatic suggestions (same display name, same local part across domains); merging only manually by the user. | 2026-10-20 |
| D3 | HTML bodies (SPEC 9) | Displayed only in a sandboxed iframe. Text is extracted from HTML for the full-text index only when the mail has no text part. | 2026-10-20 |
| D4 | Access protection (SPEC 9) | No login by default; optional HTTP Basic Auth via two environment variables. | 2026-10-20 |
| D5 | Gephi export (SPEC 9) | GraphML export of the current graph excerpt in the UI, plus a CLI command exporting the complete graph from the `edge` table. | 2026-10-20 |
| D6 | Repository workflow | One pull request per milestone against `main`, merged by Claude once lint, typecheck, tests and CI are green. Aaron is assigned and requested as reviewer but not waited for. | 2026-10-20 |
| D7 | Target machine | macOS or Linux, about 10 GB RAM for Postgres and the importer together, Docker Desktop or Linux Docker. Compose defaults: `shared_buffers` 2 GB, `maintenance_work_mem` 1 GB, importer workers `min(8, CPU count)`. | 2026-10-20 |
| D8 | Stack details | uv, Python 3.12, SQLAlchemy 2 async with asyncpg, Alembic, ruff, mypy (strict), pytest. Graph rendering with Cytoscape.js only (no Sigma.js), with the hard limit of 2,000 nodes per view from SPEC 5.4. | 2026-10-20 |
| D9 | Name | The tool is called Mailrobbe (formerly Mailspider). Package, CLI and environment prefix follow (`mailrobbe`, `MAILROBBE_`); Aaron renames the GitHub repository later. | 2026-10-20 |
| D10 | DKIM verdicts for archived mail (SPEC 3.4) | The check is cryptographic: `t=` and `x=` are recorded but do not decide, so an expired signature that still verifies is `pass`. rsa-sha256, rsa-sha1 and ed25519-sha256 are verified; RSA keys below 1024 bits are `fail`. A signature that cannot be parsed is `fail` (no separate permerror status). Every non-pass result carries a stable reason code (`DkimReason`). Mails without a signature get `unsigned` and no `dkim_result` rows. | 2026-10-20 |
| D11 | DKIM key lookups and cache (SPEC 3.4) | Key sources in order: the in-process cache (preloaded from `dns_cache`), the DNS override table (`MAILROBBE_DKIM_DNS_OVERRIDE`, or the generator's table in the MBOX directory), reserved TLDs (`.example`, `.test`, `.invalid`, `.localhost`) as not found without a query, then real DNS via dnspython (5 s per name). Answers are reused: found 7 days, not found 1 day, temp_error 10 minutes. `MAILROBBE_DKIM_OFFLINE=1` uses the cache only and turns misses into `temp_error` (`dns_offline`). A recheck asks again for every key that was missing or timed out. | 2026-10-20 |
| D12 | DKIM alignment (SPEC 3.4) | `aligned` is true when the From domain equals `d=` or one is a subdomain of the other (relaxed alignment without a public suffix list); unknown without exactly one From address. | 2026-10-20 |
| D13 | DKIM recheck (SPEC 3.4) | `mailrobbe dkim` reads mails back from their MBOX files and checks them in a process pool; by default those not checked yet and those with `no_key` or `temp_error`, selectable by status or mail id. The importer checks inline with one `DkimChecker` per worker. | 2026-10-20 |
| D14 | MBOX discovery and changed files (milestone 2) | Every regular file below `MAILROBBE_MBOX_DIR` whose first bytes are `From ` is an MBOX file, whatever its name; hidden entries and `_generator/` are skipped. `mbox_file.path` is relative to that directory. A file that grew is continued at its last committed record; one whose first MiB changed or that shrank below its progress is imported again from scratch. | 2026-10-20 |
| D15 | Importer parallelism | One worker process per MBOX file (no byte ranges), started with spawn; each batch commits its mails together with the file's progress, which makes interrupted imports resumable and idempotent. | 2026-10-20 |
| D16 | Duplicates | A mail is a duplicate of the earliest mail (by file path, then byte offset) with the same Message-ID and subject, or, when it has no Message-ID, the same SHA-256 of the raw message. Computed after the import, not while it runs. | 2026-10-20 |
| D17 | Threads | Mails are linked through Message-ID, In-Reply-To and References; `thread_id` is the smallest mail id of a thread with at least two mails and NULL for a single mail. Duplicates take the thread of their original. | 2026-10-20 |
| D18 | Full text and size limits | `mail.tsv` is a generated column with the German text search configuration, subject weighted A, body B; `body_text` is cut at 50,000 characters. Attachments above 50 MiB are not hashed; mails above 128 MiB are imported with their headers only (parsing needs up to about 8 times a mail's size, so one worker stays below about 1 GB). Both limits are settings. | 2026-10-20 |
| D19 | Mail list paging and counts (milestone 4, SPEC 5.1, 6) | Keyset pages of 50 on (date, id), newest first by default, mails without a date as the oldest; the UI pages with Zurück/Weiter instead of page numbers, since jumping to page N needs OFFSET, which is slow at 400,000 mails. Counts of a filtered list are exact within `MAILROBBE_API_COUNT_TIMEOUT` (2 s), otherwise "mehr als 10.000". Unfiltered figures and the counters next to the filters come from `global_stats`, recomputed after each import, after `mailrobbe dkim` and by the API when older than `MAILROBBE_STATS_MAX_AGE` (5 minutes). | 2026-10-21 |
| D20 | Search syntax (SPEC 4) | `from:`, `to:`, `cc:` match part of an address or display name (pg_trgm); `domain:` any participant's domain or a subdomain of it; `subject:` part of the subject (pg_trgm, so `Vertrag` also finds `Vertragsentwurf`); `has:attachment`; `dkim:` one of pass, fail, no_key, unsigned, temp_error, unchecked; `after:` and `before:` take YYYY-MM-DD (after inclusive, before exclusive, UTC); values may be quoted. A bare `<id@host>` finds that Message-ID. The rest is full text (`websearch_to_tsquery`, German configuration). All terms must hold; an operator with an unusable value is an error naming the term, not full text. | 2026-10-21 |
| D21 | Filter column (SPEC 5.1) | DKIM statuses and sender domains are each "any of"; Zeitraum is in UTC days, both ends inclusive. "Nur extern ↔ intern" is offered only when `MAILROBBE_INTERNAL_DOMAINS` lists the owner's domains: a mail qualifies when the sender is internal and a recipient external, or the other way round (subdomains count as internal). | 2026-10-21 |
| D22 | Mail bodies in the detail view (SPEC 5.2, D3) | Read on demand from the MBOX file and checked against `raw_sha256`; a missing or changed file shows an error instead of other bytes. The text tab shows the part the importer indexes, in full up to 1 million characters. HTML only in an iframe with an empty `sandbox` attribute, served with a `Content-Security-Policy` that allows inline styles and `data:` images and nothing else, so no script runs and nothing is loaded from outside; images referenced by `cid:` are not shown yet. The raw view shows up to 2 MiB; the EML download has the whole message. | 2026-10-21 |
| D23 | Flags and notes (SPEC 5.2 "Markieren/Notiz") | One flag and one free-text note per mail in the table `mail_note`, the only data users write; the mail list can filter for flagged mails. | 2026-10-21 |
| D24 | Serving the web UI (D1, D4) | FastAPI serves the built frontend from `MAILROBBE_FRONTEND_DIR` (default `frontend/dist`, `/app/frontend/dist` in the image) with `index.html` for every client-side route; the Docker image builds it in a Node stage, so `docker compose up -d --build` delivers everything. Basic Auth is on when `MAILROBBE_BASIC_AUTH_USER` and `MAILROBBE_BASIC_AUTH_PASSWORD` are both set (only one is a startup error) and covers everything but `/api/health`. | 2026-10-21 |
| D25 | CSV export (SPEC 5.1) | Every mail of the current filter, streamed, metadata only (no bodies); semicolon-separated UTF-8 with a byte order mark, so it opens directly in Excel with German settings. | 2026-10-21 |
| D26 | Person figures in the mail detail (SPEC 5.2) | The participants' mail and contact counts and their mails with the sender come from `person_stats` and `edge` (SPEC 6.3), which milestone 5 fills; until then the detail view leaves them out. | 2026-10-21 |
| D27 | Frontend libraries (D1) | React Router for routes, TanStack Query for fetching (caching between list and detail, cancellation, polling for the import state), fonts self-hosted through Fontsource (no requests to Google), CSS modules on the design tokens of SPEC 7, inline SVG icons, no component library; ESLint, Prettier and Vitest for checks. Node 22 LTS, npm with a lock file. | 2026-10-21 |
| D28 | Persons and merging (D2, SPEC 5.3, milestone 5) | A person is a root person: its own address plus the addresses merged into it (aliases). `person.merged_into` always names a root, since merging re-points the aliases of a merged person too, so the root of an address is `coalesce(merged_into, id)`. Merging (one target, one or more sources) and unmerging an alias happen only by the user's click; dismissing a suggestion stores the pair in `alias_dismissal`. Merges and dismissals are user data like `mail_note` and survive re-imports. A link to an alias opens its root's profile, and the figures in the mail detail (D26) are those of the participants' roots. | 2026-10-21 |
| D29 | Person figures (SPEC 3.3, 5.3) | Per root person, over the mails that are not duplicates: sent = the person is in From; received = in To, Cc or Bcc but not in From; only Cc = received with the person in Cc alone; first and last mail over both; DKIM share = pass among the sent mails that were checked (no figure when none was); contacts = the person's rows in `edge` (milestone 6: from the sender to each recipient, between roots, without duplicates). `person_year` holds sent and received per UTC year; mails without a date count in the totals only. | 2026-10-21 |
| D30 | Alias suggestions (D2) | Two root persons are suggested as one when they share a display name or a local part. Display names: every name used with one of their addresses, lowercased, "Nachname, Vorname" turned around, quotes and surplus spaces removed, at least two words and no `@`. Local parts: lowercased, without a `+suffix`, not a role address such as info@ or noreply@. A name or local part shared by more than five persons is too generic and suggests nothing. Dismissed pairs and the aliases of one root are never suggested. Suggestions show in the profile and as a list on the persons screen; merging stays a click by the user. | 2026-10-21 |
| D31 | Person list (SPEC 4, 5.3) | Root persons once their mails are aggregated (D33), 50 per page with keyset paging as in D19, sorted by mails (default), by name or by latest mail. The search matches part of any address or display name of the person or its aliases (pg_trgm). The total is exact, since there are far fewer persons than mails. | 2026-10-21 |
| D32 | A person's mails (SPEC 5.3) | The mail list with `person=<id>`, `person_role` (sent, received or Cc only as in D29), the year as a date range, `between` the person and a contact, and duplicates hidden, so the tab counts match the figures; paging, the neighbours in the detail view and the CSV export are those of the mail list. Each row shows the person's role (Von, An, Cc, Bcc; the first when it has several). Tab counts for a year or a contact come from `/api/persons/{id}/mail-counts` under the count budget of D19. | 2026-10-21 |
| D33 | When aggregates are computed | `aggregates.refresh_aggregates` recomputes edges, person figures, alias suggestions and `global_stats`, in this order, after every import (finalize) and after `mailrobbe dkim`; a merge or unmerge recomputes them for the persons concerned before the request returns. The API never recomputes person figures lazily, since a full run takes seconds at 400,000 mails, so the persons of a running import appear after its finalize, and a DKIM recheck of one mail in the UI changes the DKIM share at the next run. | 2026-10-21 |
| D34 | Milestones 5 and 6 side by side | Milestone 6 owns `edge`, `edge_year` and `person.kind` (`graph/edges.py`, `refresh_edges(db, persons)`); milestone 5 owns `person_stats`, `person_year`, alias suggestions and merges (`persons/`) and reads `edge` for contacts and top contacts. Both count root persons and leave duplicates out. Decision numbers D28 to D35 belong to milestone 5, D36 onward to milestone 6. | 2026-10-21 |
