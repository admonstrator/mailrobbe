| D9 | Name | The tool is called Mailrobbe (formerly Mailspider). Package, CLI and environment prefix follow (`mailrobbe`, `MAILROBBE_`); Aaron renamed the GitHub repository to `admonstrator/mailrobbe` on 2026-10-21. | 2026-10-20 |
| D10 | DKIM verdicts for archived mail (SPEC 3.4) | The check is cryptographic: `t=` and `x=` are recorded but do not decide, so an expired signature that still verifies is `pass`. rsa-sha256, rsa-sha1 and ed25519-sha256 are verified; RSA keys below 1024 bits are `fail`. A signature that cannot be parsed is `fail` (no separate permerror status). Every non-pass result carries a stable reason code (`DkimReason`). Mails without a signature get `unsigned` and no `dkim_result` rows. | 2026-10-20 |
| D11 | DKIM key lookups and cache (SPEC 3.4) | Key sources in order: the in-process cache (preloaded from `dns_cache`), the DNS override table (`MAILROBBE_DKIM_DNS_OVERRIDE`, or the generator's table in the MBOX directory), reserved TLDs (`.example`, `.test`, `.invalid`, `.localhost`) as not found without a query, then real DNS via dnspython (5 s per name). Answers are reused: found 7 days, not found 1 day, temp_error 10 minutes. `MAILROBBE_DKIM_OFFLINE=1` uses the cache only and turns misses into `temp_error` (`dns_offline`). A recheck asks again for every key that was missing or timed out. | 2026-10-20 |
| D12 | DKIM alignment (SPEC 3.4) | `aligned` is true when the From domain equals `d=` or one is a subdomain of the other (relaxed alignment without a public suffix list); unknown without exactly one From address. | 2026-10-20 |
| D13 | DKIM recheck (SPEC 3.4) | `mailrobbe dkim` reads mails back from their MBOX files and checks them in a process pool; by default those not checked yet and those with `no_key` or `temp_error`, selectable by status or mail id. The importer checks inline with one `DkimChecker` per worker. | 2026-10-20 |
| D14 | MBOX discovery and changed files (milestone 2) | Every regular file below `MAILROBBE_MBOX_DIR` whose first bytes are `From ` is an MBOX file, whatever its name; hidden entries and `_generator/` are skipped. `mbox_file.path` is relative to that directory. A file that grew is continued at its last committed record; one whose first MiB changed or that shrank below its progress is imported again from scratch. | 2026-10-20 |
| D15 | Importer parallelism | One worker process per MBOX file (no byte ranges), started with spawn; each batch commits its mails together with the file's progress, which makes interrupted imports resumable and idempotent. | 2026-10-20 |
| D16 | Duplicates | A mail is a duplicate of the earliest mail (by file path, then byte offset) with the same Message-ID and subject, or, when it has no Message-ID, the same SHA-256 of the raw message. Computed after the import, not while it runs. | 2026-10-20 |
| D17 | Threads | Mails are linked through Message-ID, In-Reply-To and References; `thread_id` is the smallest mail id of a thread with at least two mails and NULL for a single mail. Duplicates take the thread of their original. | 2026-10-20 |
| D18 | Full text and size limits | `mail.tsv` is a generated column with the German text search configuration, subject weighted A, body B; `body_text` is cut at 50,000 characters. Attachments above 50 MiB are not hashed; mails above 128 MiB are imported with their headers only (parsing needs up to about 8 times a mail's size, so one worker stays below about 1 GB). Both limits are settings. | 2026-10-20 |
| D19 | Mail list paging and counts (milestone 4, SPEC 5.1, 6) | Keyset pages of 50 on (date, id), newest first by default, mails without a date as the oldest; the UI pages with Zurück/Weiter instead of page numbers, since jumping to page N needs OFFSET, which is slow at 400,000 mails. Counts of a filtered list are exact within `MAILROBBE_API_COUNT_TIMEOUT` (2 s), otherwise "mehr als 10.000". Unfiltered figures and the counters next to the filters come from `global_stats`, recomputed after each import, after `mailrobbe dkim` and by the API when older than `MAILROBBE_STATS_MAX_AGE` (5 minutes). | 2026-10-21 |
| D20 | Search syntax (SPEC 4) | `from:`, `to:`, `cc:` match part of an address or display name (pg_trgm); `domain:` any participant's domain or a subdomain of it; `subject:` part of the subject (pg_trgm, so `Vertrag` also finds `Vertragsentwurf`); `has:attachment`; `dkim:` one of pass, fail, no_key, unsigned, temp_error, unchecked; `after:` and `before:` take YYYY-MM-DD (after inclusive, before exclusive, UTC); values may be quoted. A bare `<id@host>` finds that Message-ID. The rest is full text (`websearch_to_tsquery`, German configuration). All terms must hold; an operator with an unusable value is an error naming the term, not full text. | 2026-10-21 |
| D21 | Filter column (SPEC 5.1) | DKIM statuses and sender domains are each "any of"; Zeitraum is in UTC days, both ends inclusive. "Nur extern ↔ intern" is offered only when `MAILROBBE_INTERNAL_DOMAINS` lists the owner's domains: a mail qualifies when the sender is internal and a recipient external, or the other way round (subdomains count as internal). | 2026-10-21 |
| D22 | Mail bodies in the detail view (SPEC 5.2, D3) | Read on demand from the MBOX file and checked against `raw_sha256`; a missing or changed file shows an error instead of other bytes. The text tab shows the part the importer indexes, in full up to 1 million characters. HTML only in an iframe with an empty `sandbox` attribute, served with a `Content-Security-Policy` that allows inline styles and `data:` images and nothing else, so no script runs and nothing is loaded from outside; images referenced by `cid:` are not shown yet. The raw view shows up to 2 MiB; the EML download has the whole message. | 2026-10-21 |
| D23 | Flags and notes (SPEC 5.2 "Markieren/Notiz") | One flag and one free-text note per mail in the table `mail_note`, the only data users write; the mail list can filter for flagged mails. | 2026-10-21 |
| D24 | Serving the web UI (D1, D4) | FastAPI serves the built frontend from `MAILROBBE_FRONTEND_DIR` (default `frontend/dist`, `/app/frontend/dist` in the image) with `index.html` for every client-side route; the Docker image builds it in a Node stage, so `docker compose up -d --build` delivers everything. Basic Auth is on when `MAILROBBE_BASIC_AUTH_USER` and `MAILROBBE_BASIC_AUTH_PASSWORD` are both set (only one is a startup error) and covers everything but `/api/health`. | 2026-10-21 |
| D25 | CSV export (SPEC 5.1) | Every mail of the current filter, streamed, metadata only (no bodies); semicolon-separated UTF-8 with a byte order mark, so it opens directly in Excel with German settings. | 2026-10-21 |
| D26 | Person figures in the mail detail (SPEC 5.2) | The participants' mail and contact counts and their mails with the sender come from `person_stats` and `edge` (SPEC 6.3), which milestone 5 fills; until then the detail view leaves them out. | 2026-10-21 |
| D27 | Frontend libraries (D1) | React Router for routes, TanStack Query for fetching (caching between list and detail, cancellation, polling for the import state), fonts self-hosted through Fontsource (no requests to Google), CSS modules on the design tokens of SPEC 7, inline SVG icons, no component library; ESLint, Prettier and Vitest for checks. Node 22 LTS, npm with a lock file. | 2026-10-21 |
| D28 | Persons and merging (D2, SPEC 5.3, milestone 5) | A person is a root person: its own address plus the addresses merged into it (aliases). `person.merged_into` always names a root, since merging re-points the aliases of a merged person too, so the root of an address is `coalesce(merged_into, id)`. Merging (one target, one or more sources) and unmerging an alias happen only by the user's click; dismissing a suggestion stores the pair in `alias_dismissal`. Merges and dismissals are user data like `mail_note` and survive re-imports. A link to an alias opens its root's profile, and the figures in the mail detail (D26) are those of the participants' roots. | 2026-10-21 |
| D29 | Person figures (SPEC 3.3, 5.3) | Per root person, over the mails that are not duplicates: sent = the person is in From; received = in To, Cc or Bcc but not in From; only Cc = received with the person in Cc alone; first and last mail over both; DKIM share = pass among the sent mails that were checked (no figure when none was); contacts = the person's rows in `edge` (D36: the sender with each recipient, To, Bcc or Cc, between roots, without duplicates). `person_year` holds sent and received per UTC year; mails without a date count in the totals only. | 2026-10-21 |
| D30 | Alias suggestions (D2) | Two root persons are suggested as one when they share a display name or a local part. Display names: every name used with one of their addresses, lowercased, "Nachname, Vorname" turned around, quotes and surplus spaces removed, at least two words and no `@`. Local parts: lowercased, without a `+suffix`, not a role address such as info@ or noreply@. A name or local part shared by more than five persons is too generic and suggests nothing. Dismissed pairs and the aliases of one root are never suggested. Suggestions show in the profile and as a list on the persons screen; merging stays a click by the user. | 2026-10-21 |
| D31 | Person list (SPEC 4, 5.3) | Root persons once their mails are aggregated (D33), 50 per page with keyset paging as in D19, sorted by mails (default), by name or by latest mail. The search matches part of any address or display name of the person or its aliases (pg_trgm). The total is exact, since there are far fewer persons than mails. | 2026-10-21 |
| D32 | A person's mails (SPEC 5.3) | The mail list with `person=<id>`, `person_role` (sent, received or Cc only as in D29), the year as a date range, `between` the person and a contact, and duplicates hidden, so the tab counts match the figures; paging, the neighbours in the detail view and the CSV export are those of the mail list. Each row shows the person's role (Von, An, Cc, Bcc; the first when it has several). Tab counts for a year or a contact come from `/api/persons/{id}/mail-counts` under the count budget of D19. | 2026-10-21 |
| D33 | When aggregates are computed | `aggregates.refresh_aggregates` recomputes edges, person figures, alias suggestions and `global_stats`, in this order, after every import (finalize) and after `mailrobbe dkim`; a merge or unmerge recomputes them for the persons concerned before the request returns. The API never recomputes person figures lazily, since a full run takes seconds at 400,000 mails, so the persons of a running import appear after its finalize, and a DKIM recheck of one mail in the UI changes the DKIM share at the next run. | 2026-10-21 |
| D34 | Milestones 5 and 6 side by side | Milestone 6 owns `edge`, `edge_year` and `person.kind` (`graph/edges.py`, `refresh_edges(db, persons)`); milestone 5 owns `person_stats`, `person_year`, alias suggestions and merges (`persons/`) and reads `edge` for contacts and top contacts. Both count root persons and leave duplicates out. Decision numbers D28 to D35 belong to milestone 5, D36 onward to milestone 6. | 2026-10-21 |
| D35 | JIT compilation | The application's connections turn PostgreSQL's JIT compilation off (`db/session.py`), whatever the server is configured with. JIT compiles every query the planner estimates above `jit_above_cost` and added 300 ms and more to filters that then run in about 60 ms (the `between` filter of the profile at 50,000 mails: 516 ms with JIT, 85 ms without); the aggregate refresh takes the same time either way. | 2026-10-21 |
| D36 | Edges (milestone 6, SPEC 3.3, 5.4) | `edge` joins root persons (`coalesce(merged_into, id)`) and counts every mail that is no duplicate: the sender to each To or Bcc recipient in `mails_a_to_b`/`mails_b_to_a`, to each Cc recipient in `mails_cc` (either direction), once per mail and pair with To before Cc; no edge from a person to itself and none between recipients. `pass_*` count the same over the mails whose DKIM check passed. `edge_year` holds the same six counters per UTC year (its single `count` is gone); undated mails are only in `edge`. Recomputed after every import and `mailrobbe dkim`, by `mailrobbe graph refresh`, and for the persons concerned after merging or splitting addresses. | 2026-10-21 |
| D37 | Map excerpt (SPEC 5.4) | The map shows an excerpt of the counted graph: edges from `edge`, or summed from `edge_year` when a year range is set (the map's Zeitraum is in whole UTC years, matching the year-by-year playback), weighted by To/Bcc in both directions plus Cc when "Cc mitzählen" is on, over all mails or only DKIM-valid ones, without hidden persons and, on request, without lists and automated senders. Ego follows edges of at least the threshold from the centers up to depth 3, top takes the N persons with the most mails, domains the persons of two domains with an edge between them; every counted edge of at least the threshold between shown persons is drawn, centers stay even without edges. A node's size is the weight of all its counted edges. "Nachbarn aufklappen" and "Knoten ausblenden" are parameters of the excerpt, so the URL describes the whole view and the GraphML download reproduces it. More than 2,000 nodes are refused with `graph_too_large`; a size request answers for any excerpt, for the preview next to the threshold. | 2026-10-21 |
| D38 | GraphML (D5) | Undirected GraphML with node attributes label, email, domain, kind and mails and edge attributes weight, a_to_b, b_to_a and cc, plus first_date and last_date in the full export. The UI downloads the shown excerpt from `/api/graph/export.graphml` with the excerpt's parameters; `mailrobbe graph export` writes the whole `edge` table, every pair with its total, for Gephi. | 2026-10-21 |
| D39 | Lists and automated senders (SPEC 5.4) | The importer stores the List-Id of each mail (`mail.list_id`) and whether a program sent it (`mail.automated`: Auto-Submitted other than `no`, or Precedence `bulk`, `junk` or `auto_reply`; Precedence `list` alone is a person posting to a list). `refresh_edges` sets `person.kind` for every root person from its own addresses and mails: `automated` for a noreply-style local part, when more than half of its sent mails are automated or bulk (a List-Id naming none of the recipients), or when it sent at least 10 mails, none of them a reply or list post, and never received one; otherwise `list` for an address that is the List-Id of a mail it received (`local@domain` against `local.domain`), or for one that never sent, got mails from at least 10 different senders as the only recipient and never a list or newsletter mail (distribution lists expanded by a mail server carry no List-Id). Merged addresses have no kind. "Verteiler und Automaten ausblenden" hides both. Mails imported before milestone 6 lack the two header columns; the rule then relies on addresses and communication patterns only, so the archive should be imported afresh. | 2026-10-21 |
| D40 | Excerpt details (D37) | `center` only counts in the ego mode and is ignored in the others, so switching modes keeps the URL valid. Domain values are trimmed, lowercased and stripped of a leading `@`; a side consists of the root persons whose own domain is the named one or a subdomain of it. Hiding lists never hides a center, `expand` does not bring back a hidden person, and hiding an alias hides its root. An excerpt above 2,000 nodes is counted to the end, so the refusal names its size. | 2026-10-21 |
| D41 | Map layouts (SPEC 5.4) | Four layouts of our own, deterministic and computed in the browser instead of Cytoscape's `cose`, which takes seconds at 2,000 nodes and starts at random: force (ForceAtlas2-like with Barnes-Hut, starting on a spiral), domain clusters (the largest domain in the middle, the others on rings), circle grouped by domain, and hierarchical as rings by distance from the centers (for top and domains from the heaviest node). The same excerpt always gives the same picture. | 2026-10-21 |
| D42 | Map controls (SPEC 5.4, D37) | The URL of `/karte` holds the excerpt (`mode`, `center`, `depth`, `limit`, `domain`, `min`, `from`, `to`, `dkim`, `cc`, `lists`, `expand`, `hide`) and the view (`layout`, `color`, `arrows`), defaults left out. The left column edits a draft whose size is previewed next to the threshold; "Karte zeichnen" writes it into the URL. Layout, colours and arrows apply at once without a new request. The threshold is a slider from 1 to 500 with a field for the exact value. | 2026-10-21 |
| D43 | Map drawing (SPEC 5.4, 7) | Node diameter 12 to 64 px and edge width 1 to 9 px, both by square root of mails and weight; the eight domains with the most nodes in the excerpt get fixed colours, the rest grey ("sonstige"); numbers on the 12 strongest edges; lists and automated senders hollow with a dashed border. From 4,000 edges the map draws simple edges and hides them while panning and zooming. Cytoscape is loaded in its own chunk with the map screen. | 2026-10-21 |
| D44 | Year-by-year playback (SPEC 5.4) | Steps through the years of the draft's Zeitraum, or of the archive when none is set, 1.5 s per year once the year has loaded; nodes already placed keep their position. It stops at the end or on an error, and stopping leaves the shown year in the URL. | 2026-10-21 |
| D45 | Map export (SPEC 5.4, D5, D38) | PNG at twice the screen resolution, at most 8,000 px; SVG written from the same drawing data as the map; GraphML from `/api/graph/export.graphml` with the excerpt's parameters. Files are named `mailrobbe-karte.png`, `.svg` and `.graphml`. | 2026-10-21 |
| D46 | Import control from the dashboard (milestone 7, SPEC 4, 5.5) | The dashboard starts `mailrobbe import` and `mailrobbe dkim` as child processes of the API server (same container, settings and MBOX mount; their output goes to the server's log) and stops any run, also one started on a command line, through `job.stop_requested`, which the run reads every 2 s. A stopped run ends as after Ctrl-C: an import keeps its committed batches and pauses its files (D15), and the next start resumes them. One run at a time: the dashboard starts neither while an import or a DKIM run is alive. When the server stops (`docker compose stop`, a rebuild), it sends its runs SIGTERM and waits for them within the backend's stop grace period. "DKIM für „Schlüssel fehlt" neu prüfen" checks the mails of D13 (not checked yet, no_key, temp_error). | 2026-10-21 |
| D47 | Runs (`job` table) | Every `mailrobbe import` and `mailrobbe dkim` run records itself in `job` (kind, origin `cli` or `ui`, status running, done, stopped or failed, phase, options, live figures, one-line message) and holds an advisory lock of its kind from start to end; `mailrobbe dkim` takes one now too, so two DKIM runs exclude each other. A run reports every 2 s: mails/s, DKIM-checked mails/s and MB/s over the last 60 s, and the remaining time as the bytes left in its files over that byte rate. A row still running whose lock nobody holds belongs to a process that died: the dashboard shows it as aborted, and the next run of its kind marks it failed. The phases of an import are scan, headers (D52), import and finalize, those of a DKIM run check and aggregates. | 2026-10-21 |
| D48 | Dashboard figures (SPEC 5.5) | Files, progress, workers, throughput and errors are read live from `mbox_file`, `import_error` and `job`, polled every 2 s while a run is alive and every 15 s otherwise; the expected number of mails is extrapolated from the bytes done ("ca."). Database size and full text index come from PostgreSQL's size functions, the DNS cache from `dns_cache`. The DKIM distribution, the reasons of failed checks (mails with status fail per reason of a failing signature), the DNS cache hit share (signatures whose key came from the cache), duplicates, persons, open alias suggestions and the edge table come from `global_stats`, recomputed when an import ends or pauses and otherwise at most 5 minutes old (D19), with their time shown. Parsing and DKIM throughput are nearly equal, since the importer checks DKIM inline (D13). | 2026-10-21 |
| D49 | Settings in the dashboard (SPEC 5.5) | Workers, the attachment hash limit and the DNS resolvers apply to the next import started from the dashboard; they are stored with that run (`job.options`) and prefill the next start. The environment (`.env`) stays the default, and command line runs keep their own flags. Full text indexing cannot be switched off: `mail.tsv` is a generated column (D18), and mails imported without text could only become searchable by importing them again. | 2026-10-21 |
| D50 | Rescanning the MBOX directory (SPEC 5.5) | "Verzeichnis neu scannen" runs the importer's scan (D14) in the server while no import runs and lists new, changed, missing and unreadable files; a changed file loses its mails at once, as at the start of an import, and the next import reads it again. During an import the button is disabled: the run works through the files it found at its start. | 2026-10-21 |
| D51 | Load test (milestone 7) | `mailrobbe bench` measures the API of a running server the way one person clicks through the screens: sequential requests, p50, p95 and maximum per view, with samples (mails, persons, words, domains) picked through the API itself, so it runs on the host or in the container against any archive. The load test imports 400,000 generated mails and measures import, aggregation and every view; docs/LOADTEST.md holds the procedure and the results. | 2026-10-21 |
| D52 | Header refresh for older imports (D39) | `mbox_file.header_version` marks files whose mails have every header field the importer parses (version 1: `list_id` and `automated`). An import first reads the header block of every stored mail of an older file again, in file order, updates the two columns and raises the version, then imports as usual; finalize recomputes `person.kind`. Archives imported before milestone 6 thus get the list and automation detection without a new import, and notes, merges and DKIM results stay. | 2026-10-21 |
| D53 | Research data and mail identity (milestone 8) | Everything the research file records about a mail (bookmark, review status, notes, tags, Akten) is keyed by the mail's raw SHA-256 (`mail_sha256`) instead of `mail.id`, without a foreign key to `mail`: it survives a re-import of a changed file and a rebuilt database, and byte-identical copies of a mail share it. Rows whose content is no longer in the archive stay and are counted as missing. Tags, Akten, saved searches and exports have ids of their own. | 2026-10-21 |
| D54 | Editor name (milestone 8) | Until named accounts exist, the web UI asks for a name once, keeps it in the browser and sends it with every write as `X-Mailrobbe-Editor` (percent-encoded UTF-8, at most 100 characters kept); the backend stores it as the author of notes and the editor of marks, links and exports, NULL without one. It is attribution, not authentication: anyone can enter any name. | 2026-10-21 |
| D55 | Review status and bookmark (replaces D23's flag) | One team-wide review status per mail (none = ungesichtet, gesichtet, relevant, nicht relevant) and the bookmark ("Markiert", the flag of D23), each with who set it and when, in `mail_mark`. Opening a mail sets nothing; the detail view sets the status by click or key. The list filters by status (`review`, any of, `unreviewed` for none) and bookmark (`flagged`). | 2026-10-21 |
| D56 | Notes (replaces D23's note) | Any number of notes per mail, each with author, creation and edit time, up to 10,000 characters; anyone may edit or delete any note, since there are no accounts yet. Migration 0007 turns the single note of D23 into a note without author. The Akten screen lists every note, newest first, and searches their text (substring, pg_trgm). Filter `has_note`. | 2026-10-21 |
| D57 | Tags | Free names, unique ignoring case, at most 60 characters, a colour from a fixed palette of eight and an optional description; any number per mail. Deleting a tag removes it from every mail. Filter `tag`: any of the given tags. | 2026-10-21 |
| D58 | Akten (collections) | An Akte is a named collection of mails with a description, for a story or a question; a mail can be in several. Its page shows its mails, date range, the persons most involved, its saved searches and the export. Deleting an Akte deletes only the membership, never mails, notes or tags. Filter `collection`: in any of the given Akten. | 2026-10-21 |
| D59 | Saved searches | A name plus the query string of the mail list (search text, filters, sort), optionally belonging to an Akte. Opening one runs it anew, so its matches follow the archive and the research data. | 2026-10-21 |
| D60 | Bulk changes | The mail list applies a tag, an Akte, a review status or the bookmark, or removes a tag or Akte, for the selected mails (up to 1,000 ids) or for every mail matching the current filters (up to 50,000; more are refused with `too_many_mails`) in one request. The selection by filter is exactly what the list shows (`api/selection.py`). A bulk change analyses the table it changed in the same transaction, so the next list with that filter is planned on the new numbers. | 2026-10-21 |
| D61 | Permalinks | `/m/<first 16 hex digits of the raw SHA-256>` opens a mail by its content, so the link holds after a re-import and in any Mailrobbe with the same archive; prefixes of 12 to 64 digits are accepted, a prefix shared by different contents is `ambiguous_permalink`, byte-identical copies open the original. Akten have `/akten/<id>`; a saved search is a mail list URL. | 2026-10-21 |
| D62 | Export for lawyers and archives | `POST /api/exports` records an export of up to 2,000 mails (selection, filters or an Akte) with who asked, the mails in order (oldest first) and options; `GET /api/exports/{id}/download` streams a ZIP: per mail a folder `NNNN-<id>/` with `mail.eml` (the MBOX record's bytes unchanged, checked against the SHA-256 stored at import) and `mail.pdf`, plus `manifest.json`, `manifest.csv` (id, Message-ID, date, sender, recipients, subject, source file and offset, SHA-256 of every file, DKIM result per signature), `SHA256SUMS` (every other file, for `sha256sum -c`) and `LIESMICH.txt` (what the files are and how to check them). Notes, tags, status and Akten go in only on request (`include_research`), so internal assessments and sources are not handed out by accident; the same holds for the selection itself (ids, filters, search text), which can reveal what the team suspects. Byte-identical copies go in once. A mail whose bytes no longer match is listed with its error and without files.
